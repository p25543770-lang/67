# Depth Studio

Depth Studio — приложение для просмотра потока глубины и экспериментального сканирования помещения. Есть автономный деморежим и модульная архитектура источников данных.

> **Честный статус датчиков.** Для Kinect 360 / Kinect v1 реализованы **два** экспериментальных пути чтения: рекомендуемый адаптер через **Microsoft Kinect SDK 1.8** (штатный драйвер Microsoft Kinect остаётся как есть) и альтернативный через **libfreenect** с USB-драйвером libusbK/WinUSB. Ни один из них пока **не проверен на физическом датчике** в этом репозитории, поэтому в интерфейсе оба помечены как экспериментальные (`verifiedOnHardware = false`). Kinect One (v2), Azure Kinect и Intel RealSense перечислены в интерфейсе и документации, но их интеграционные модули пока не реализованы и источники отключены. Обычная RGB-камера не считается датчиком глубины.

## Что умеет приложение

- Работать в деморежиме без датчика, Python, драйверов и локального моста; демо показывает и экспортирует синтетическое **облако точек** в PLY/OBJ.
- Обнаруживать датчик, затем отдельно подключать выбранный источник; показывать RGB и карту глубины, если соответствующие кадры доступны.
- Использовать экспериментальный конвейер `scan_pipeline`: TSDF-объём и отслеживание frame-to-model ICP через Open3D. По умолчанию ICP геометрический, цветной ICP отключён.
- Показывать потерю трекинга, слишком быстрое движение, недостаток валидной глубины и возможно закрытый датчик.
- Сохранять проходы на диск, продолжать прерванный проход и объединять завершённые проходы; ошибки совмещения отображаются и неуспешные проходы исключаются из объединения.
- После обработки экспортировать результат датчика как сетку с гранями, нормалями и **вершинными цветами** в PLY (binary), OBJ или GLB. UV-развёртка и отдельная текстура не создаются.

В 3D-окне результат показывается точками, а не полигональной сеткой. Геометрия и цвет могут быть неточными: ICP может дрейфовать на однотонных стенах, при резком движении, недостаточном перекрытии или движущихся объектах; RGB и глубина Kinect v1 не совмещены, калибровка приблизительная. Конвейер проверялся на синтетических данных, **на физическом датчике не проверен**. Это исследовательский прототип, а не измерительный инструмент.

## Установка и первый запуск (Windows x64)

1. Скачайте `Depth-Studio-Setup-<версия>-x64.exe` по ссылке из раздела «Скачать» (релиз `installer-latest`) либо из артефакта **Depth-Studio-Windows-Installer** успешного запуска workflow **Build Windows installer**, либо соберите его сами (см. «Сборка установщика»).
2. Запустите установщик обычным двойным щелчком. Установка идёт в профиль пользователя (`%LOCALAPPDATA%\Programs\Depth Studio`), **права администратора не нужны**. SmartScreen может предупредить, потому что установщик не подписан сертификатом.
3. Запустите **Depth Studio** ярлыком с рабочего стола или из меню «Пуск» — тоже обычным двойным щелчком. Никакой терминал, `pip` или переменные окружения не нужны.
4. При первом запуске открывается экран **«Настройка среды»** с этапами, прогрессом, кнопкой повтора и журналом установки:
   1. подготовка каталога `%LOCALAPPDATA%\DepthStudio`;
   2. Python 3.11.9 x64 — копируется из установщика (офлайн);
   3. NumPy + Open3D — устанавливаются из входящих в установщик колёс;
   4. проверка импорта и изоляции интерпретатора;
   5. только чтение: раздельно «драйвер устройства» (например, Kinect for Windows SDK 1.8) и «компоненты Python» (NumPy, Open3D, pythonnet). Ничего не устанавливается.
5. После завершения этапов автоматически открывается окно сканирования. Деморежим доступен в любом случае: даже если настройка не удалась, приложение запускается и объясняет, что делать, а окно сканирования не выдаёт себя за готовое к работе с датчиком.

Повторные запуски используют уже готовую среду и не переустанавливают пакеты. Кнопка **«Восстановить среду»** на экране настройки (и в справке приложения) удаляет только `runtime\python` и создаёт среду заново; настройки и облака точек не затрагиваются.

### Сборка установщика

На Windows x64 с Node.js 20+ и Python 3.11 (Python нужен только во время сборки, чтобы скачать колёса):

```powershell
npm ci
npm run build:win
```

`npm run build:win` собирает встроенную среду (`npm run prepare:python`), рендерер и NSIS-установщик. Готовый файл — `release/Depth-Studio-Setup-<версия>-x64.exe`.

Workflow **Build Windows installer** делает то же самое в CI: собирает рендерер и встроенную среду Python, упаковывает `.exe`, проверяет его состав и запускает установщик в чистой Windows-среде (см. «Как проверяется установщик»). Артефакт — **Depth-Studio-Windows-Installer**.

### Что входит в установщик

- Интерфейс (Vite/Electron), Python-мост (`server.py`, `sensor_drivers/`, `scan_pipeline/`), документация.
- Официальный **Python 3.11.9 embeddable (x64)** с python.org (SHA-256 архива закреплён в `python-lock.json`), `Lib\site-packages` и каталог приложения прописаны в `python311._pth`.
- 64 колеса с закреплёнными версиями и SHA-256: `numpy==1.26.4`, `open3d==0.18.0`, `pythonnet==3.2.1` (мост к .NET для Kinect SDK 1.8) и весь транзитивный набор, включая `clr-loader==0.3.1`, `cffi==2.1.1`, `pycparser==3.12` и Windows-зависимость `colorama==0.4.6` (`python-lock.json`, `requirements-scan.lock.txt`), плюс `pip==24.2` для установки.
- USB-драйверы, SDK датчиков и системные компоненты **не входят** и не устанавливаются автоматически.

Измеренные размеры (проверка CI): установщик ≈ 247 МБ, установленное приложение ≈ 543 МБ, встроенные артефакты Python ≈ 142 МБ (MiB), среда первого запуска в `%LOCALAPPDATA%` ≈ 447 МиБ. Всего на диске нужно около 1 ГБ.

Распаковка архивов выполняется встроенным распаковщиком приложения на Node.js, а не через PowerShell: установка не зависит от политик PowerShell (`ExecutionPolicy`) и не требует внешних утилит. pip ставится распаковкой его колеса в `Lib\site-packages` — команда `pip install pip` для встроенного интерпретатора намеренно не используется.

Если в сборке нет встроенной среды (например, её исключили при сборке), первый запуск переходит в резервный режим: скачивает архив Python с `python.org` и колёса с PyPI по закреплённым версиям, проверяет SHA-256 каждого файла, показывает прогресс и понятные ошибки. Проверка TLS при этом всегда включена. Если SHA-256 архива Python не закреплён в `python-lock.json`, резервный путь отказывается работать и предлагает официальный установщик — непроверенные артефакты не скачиваются. Проверка TLS при загрузке всегда включена, флаги вида `--trusted-host` и отключение проверки сертификатов не используются.

### Архитектура датчиков

Каждый источник находится в своём модуле каталога `sensor_drivers/` и следует контракту `SensorAdapter` из `sensor_drivers/base.py`. Каталог сообщает отдельно о наличии реализации, зависимостей и аппаратной проверки. Будущие адаптеры нельзя отмечать как поддержку только по факту установленного SDK; перед включением источника нужны функциональные тесты с реальным датчиком.

## Kinect 360 (Kinect v1): два варианта

Оба адаптера читают один и тот же сенсор. При обнаружении приложение сначала проверяет рекомендуемый адаптер и не опрашивает повторно найденный датчик через второй; выбранную альтернативу можно подключить отдельно. Пробный дескриптор освобождается после обнаружения. Открытый сенсор освобождается (`Stop` → `Disable` → `Dispose`) при отключении, остановке сканирования и закрытии приложения.

### Вариант 1 — Microsoft Kinect SDK 1.8 (рекомендуется)

Этот путь подходит, если Kinect **уже работает** в других приложениях через драйвер Microsoft: в Диспетчере устройств устройство «Kinect for Windows» с компонентами Audio Array Control, Camera и Security Control. USB-драйвер при этом не меняется.

1. Проверьте, установлен ли сам SDK 1.8 (одного драйвера недостаточно):

```powershell
Test-Path "$env:ProgramFiles\Microsoft SDKs\Kinect\v1.8\Assemblies\Microsoft.Kinect.dll"
Test-Path "${env:ProgramFiles(x86)}\Microsoft SDKs\Kinect\v1.8\Assemblies\Microsoft.Kinect.dll"
```

2. Если оба пути дают `False`, установите [Kinect for Windows SDK 1.8](https://www.microsoft.com/en-us/download/details.aspx?id=40278) **вручную**. Depth Studio не скачивает и не устанавливает SDK, драйверы и системные компоненты датчиков: установка SDK обычно требует прав администратора, а самому приложению они не нужны.
3. Проверьте доступ из изолированной среды Depth Studio:

```powershell
& "$env:LOCALAPPDATA\DepthStudio\runtime\python\python.exe" -c "import clr; clr.AddReference('Microsoft.Kinect'); from Microsoft.Kinect import KinectSensor; print('сенсоров:', len(KinectSensor.KinectSensors))"
```

4. В приложении выберите источник **Kinect 360 · Microsoft Kinect SDK**, нажмите «Обнаружить датчики», затем «Подключить выбранный источник». Для сканирования нужны NumPy и Open3D — они входят в установщик.

Как устроен адаптер (`sensor_drivers/kinect_sdk_v1.py`):

- `clr.AddReference("Microsoft.Kinect")`, при необходимости — по полному пути к найденной сборке (`DEPTH_STUDIO_KINECT_SDK_DLL` позволяет указать нестандартное место);
- `KinectSensor.KinectSensors[0]`, включение `DepthStream` (640×480, 30 к/с) и `ColorStream` (RGB 640×480), `Start()`;
- кадры опрашиваются в цикле через `DepthStream.OpenNextFrame(0)` и `ColorStream.OpenNextFrame(0)`, без подписки на .NET-события; каждый кадр освобождается (`Dispose`) в `finally`;
- глубина берётся из старших битов пикселя `DepthImageFrame` (`pixel >> 3` — миллиметры), нулевые пиксели отбрасываются;
- при 30 к/с дополнительная программная пауза не вставляется: частоту задаёт сам поток SDK; ограничитель сохраняется для явно заданной частоты ниже 30. Ожидание RGB ограничено 15 мс; сенсор закрывается `Stop` → `Disable` → `Dispose`;
- кадры копируются через перегрузку SDK `CopyPixelDataTo(IntPtr, length)` прямо в буфер Python, без поэлементного прохода по CLR-массиву; при отсутствии перегрузки используется прежний вариант с массивом. Номер кадра SDK позволяет отдельно считать пропуски до чтения;
- калибровка приближённая, цвет и глубина не совмещены в общей системе координат.

Если `Microsoft.Kinect.dll` не найден, источник показывает статус «Драйвер устройства: не установлен Kinect for Windows SDK 1.8» со ссылкой на загрузку, а приложение продолжает работать в деморежиме. Если не найден `pythonnet`, это отдельная строка «Компоненты Python» — нажмите «Восстановить среду».

`pythonnet` 3.x при импорте поднимает .NET Framework, поэтому нужен **.NET Framework 4.7.1 или новее** (в Windows 10/11 он входит в систему). Если модуль установлен, а среда .NET не стартует, адаптер возвращает отдельный код `pythonnet_load_failed` с текстом исходной ошибки — это не то же самое, что отсутствующий `pythonnet`, и лечится не переустановкой колеса.

**Адаптер не проверен на физическом датчике.** `verified_on_hardware = False`, в интерфейсе честно написано «не проверено на реальном датчике».

Что именно проверяется автоматически, а что нет:

- в CI проверяются установка и **импорт `pythonnet`**, настоящие CLR-массивы, `IntPtr` и `Marshal.Copy` во встроенном Python Windows; кадры SDK при этом имитируются;
- модульные тесты адаптера работают на поддельных `clr` и `Microsoft.Kinect`: кадр глубины и цвет, отсутствие SDK, отсутствие сенсора, ошибка открытия, освобождение ресурсов, ограничение частоты;
- **не проверялись**: загрузка реальной `Microsoft.Kinect.dll` через .NET и кадры с физического Kinect на машине с установленным SDK 1.8. Если на вашей машине `import clr` или `Microsoft.Kinect` не загружается, пришлите `pip-bootstrap.log` и вывод самопроверки — это первый реальный тест этого пути.

### Вариант 2 — libfreenect + Zadig (альтернатива, конфликтует с драйвером Microsoft)

> ⚠️ **Предупреждение.** На Windows libfreenect работает только после привязки Kinect к драйверу **libusbK/WinUSB** (обычно через [Zadig](https://zadig.akeo.ie/)). Это **снимает штатный драйвер Microsoft Kinect**, и другие программы, которые сейчас сканируют этим же Kinect, могут перестать работать. Depth Studio не меняет USB-драйверы, не скачивает Zadig и не устанавливает libfreenect. Если датчик уже работает в других приложениях — используйте вариант 1.

1. Подготовьте совместимую с вашей Windows сборку [libfreenect](https://github.com/OpenKinect/libfreenect) и её Python-привязки `freenect`. На PyPI колёс нет — только sdist, который нужно собрать MSVC **для интерпретатора Depth Studio**.
2. Привяжите устройство к libusbK/WinUSB (Zadig) и запомните, как вернуть драйвер Microsoft: Диспетчер устройств → «Обновить драйвер» → автоматический поиск, либо переустановка драйверов Kinect.
3. Проверьте импорт:

```powershell
& "$env:LOCALAPPDATA\DepthStudio\runtime\python\python.exe" -c "import freenect, numpy, open3d; print('ok')"
```

4. В приложении выберите источник **Kinect 360 · libfreenect (альтернатива)**.

Если импорт `freenect` не проходит, меню Kinect покажет диагностическую ошибку, а Depth Studio продолжит работать в деморежиме.

### Ручной запуск моста (диагностика)

```powershell
$env:DEPTH_STUDIO_ENV_ROOT = "$env:LOCALAPPDATA\DepthStudio"
$env:DEPTH_STUDIO_REQUIRE_APP_ENV = "1"
& "$env:LOCALAPPDATA\DepthStudio\runtime\python\python.exe" server.py
```

При запуске удерживайте сенсор неподвижно, пока строится первая модель; затем передвигайте плавно и держите в кадре часть уже просмотренной поверхности. Цель настроек — до 7 км/ч (1,94 м/с), но это **не гарантия**: частота обработки, условия сцены и реальный Kinect требуют проверки. Если теряется трекинг или FPS обработки низкий, замедлитесь. Python-мост всегда запускается интерпретатором из `%LOCALAPPDATA%\DepthStudio`. Если мост всё же запущен «случайным» системным Python с `DEPTH_STUDIO_REQUIRE_APP_ENV=1`, он завершится с кодом 2 и объяснит причину. Мост слушает только `127.0.0.1:8765` (или свободный порт рядом); `/api/health` возвращает версию Python, список пакетов и признак изоляции среды, `/api/devices` — требования по каждому источнику.

### FPS и движение

- Kinect v1 выдаёт не больше **30 кадров/с**. Интерфейс отдельно показывает измеренные скользящие **FPS захвата / обработки** и **FPS успешного трекинга / интеграции в TSDF** за последние три секунды. FPS обработки включает и отбракованные кадры; при потере трекинга он может оставаться высоким, поэтому ориентируйтесь и на долю принятых кадров. При нехватке данных показан прочерк, при остановке потока — ноль.
- Показаны два разных счётчика: пропуски **в очереди обработки** и пропуски **до чтения SDK** по `FrameNumber`. Второй известен только для источника с надёжной последовательностью кадров (Kinect SDK); иначе показан прочерк. Не подсчитываются кадры до первого считанного кадра прохода, при сбросе последовательности точный счётчик становится неизвестен.
- Open3D/TSDF и ICP выполняются в отдельном процессе: долгий нативный вызов с GIL больше не должен останавливать Python-поток чтения датчика. Это требует копирования кадров между процессами и дополнительной памяти; на некоторых компьютерах выигрыш может быть иным. Запись ключевых кадров остаётся в ограниченной фоновой очереди; при перегрузке обработчику передаётся самый свежий кадр. При сбое процесса проход помечается прерванным, датчик освобождается. Если обработка ниже 24 к/с, появляется предупреждение. Частота захвата и особенно обработки зависит от ПК, USB и сцены; 30 FPS обработки не гарантированы.
- Новый проход по умолчанию использует профиль **«Максимум FPS»**: трекинг проверяет каждый *обработанный* кадр, но в TSDF добавляется меньше ключевых кадров (примерно после 7,5 см или 5° вместо 1,5 см или 2°; есть также ограничение по времени). Модель для трекинга обновляется каждые четыре интеграции. Это компромисс: может быть больше шума, хуже мелкие детали и устойчивость отслеживания. Профиль **«Стандарт · плотнее»** сохраняет прежние параметры; продолжение прохода всегда использует его сохранённые настройки, а не текущий выбор.
- В обоих профилях новый проход обрабатывает глубину **320×240** при входных 640×480; мелкие детали могут быть хуже. Геометрический ICP не пересчитывает ненужные нормали источника. Потоки OpenMP по умолчанию ограничены двумя (явное значение `OMP_NUM_THREADS` сохраняется).
- Порог движения составляет **7 км/ч** (≈1,94 м/с). При 30 FPS это ≈6,5 см между кадрами; при пропусках расстояние больше, и для однотонных стен или резких поворотов трекинг может потеряться раньше. Порог допускает до 6 мм ошибки оценки ICP за интервал, чтобы не отбраковывать пограничное движение из-за шума. Оценка скорости рассчитывается по времени между принятыми позами, а не по целевому FPS; при потере отслеживания она неизвестна. При несогласованном с недавним движением скачке или большом перемещении после паузы свыше 0,5 с кадр не интегрируется; резкое реальное ускорение или поворот тоже могут быть отвергнуты. После потери приложение требует возврата к последней надёжной позе и похожему виду, прежде чем вновь интегрировать кадры. Это дополнительная защита, но похожие поверхности всё равно могут ввести ICP в заблуждение.
- Ключевые кадры записываются в фоновую ограниченную очередь в NPZ без сжатия (около 0,37 МБ на 320×240 кадр); старые сжатые NPZ читаются как раньше. Остановка и отмена дожидаются записи, а при аварийном закрытии несколько последних кадров в очереди могут быть потеряны. Ошибка диска показывается в предупреждениях. При продолжении старого прохода настройки быстрого захвата обновляются, но параметры вокселя сохраняются.
- Семь километров в час проверены только на короткой синтетической траектории с известной геометрией и пропущенными кадрами. Это **не проверка на физическом Kinect** и не подтверждение устойчивого сканирования помещения на этой скорости. `verified_on_hardware` по-прежнему `False`.

Пример одного сравнения на двухъядерной Linux-среде, `OMP_NUM_THREADS=2`: одинаковые 90 заранее подготовленных кадров синтетической комнаты подавались с имитацией 30 к/с; работали очередь, запись на диск и опрос предпросмотра каждые 450 мс. Это не измерение Kinect или Windows, а частоты и ошибки сильно зависят от расписания потоков и сцены.

| Показатель | 1.2.1, стандартный профиль | 1.2.2, максимум FPS |
|---|---:|---:|
| Получено симулированных кадров / пропущено до чтения | 56 / 34 | 90 / 0 |
| Обработано / пропущено очередью | 16 / 40 | 33 / 57 |
| Успешно отслежено / интегрировано | 16 / 16 | 32 / 13 |
| Скользящий FPS захвата / обработки в конце прогона | 14,5 / 4,5 | 28,5 / 11,4 |
| Ошибка последней принятой позы | 22,1 мм | 15,2 мм |
| Максимальная ошибка интегрированной позы | 26,4 мм | 31,1 мм |

Более высокий FPS здесь получен, в частности, ценой меньшей плотности интеграции; ошибка отдельных кадров оказалась больше, даже при лучшей последней позе. При потере трекинга цифра обработки может расти, хотя полезный FPS падает. В одном более длинном прогоне на 150 кадров новый профиль получил все кадры источника, но принял для трекинга лишь 24, после чего в основном оставался в состоянии потери. Этот пример **не доказывает** такого же прироста на другом компьютере и не проверяет устройство.

Синтетический тест входит в установщик. После установки по стандартному пути его можно повторить в PowerShell (если выбран другой каталог установки, замените путь к `resources`):

```powershell
Set-Location "$env:LOCALAPPDATA\Programs\Depth Studio\resources"
$env:OMP_NUM_THREADS = "2"
& "$env:LOCALAPPDATA\DepthStudio\runtime\python\python.exe" .\scripts\benchmark-synthetic-fps.py --frames 90
```

Тест заранее строит сцены, создаёт временные файлы прохода и измеряет конвейер с имитированным источником; физический Kinect, USB и драйвер им не проверяются. Чтобы сравнить более старый исходный checkout с новым по тем же кадрам, можно использовать `--package-root <путь>`. Результаты обычно колеблются между запусками.

### Захват, проходы и экспорт

1. Дождитесь ответа Python-моста и завершения настройки среды. «Среда готова» не показывается, пока мост не ответил на `/api/health`. Если мост не отвечает, откройте журнал установки/моста и при необходимости восстановите среду.
2. Нажмите **«Обнаружить датчики»**: проверка читает пробный кадр и освобождает временный дескриптор, но не подключает поток. Для Kinect 360 проверьте штатный блок питания и USB-адаптер.
3. Выберите источник и нажмите **«Подключить выбранный источник»**. Успешное подключение подтверждается кадром глубины. Если открыть датчик не удалось, точные сообщение и подсказка видны в панели источника и в `logs\bridge.log`; наличие DLL само по себе не подтверждает наличие датчика. RGB может быть недоступен отдельно от глубины: предупреждение о нём показывается в интерфейсе и записывается в журнал. Если подключение зависло, интерфейс сообщает о тайм-ауте; нативный вызов драйвера может завершиться позже, после чего датчик будет освобождён.
4. Запустите сканирование. Для физического датчика запуск, очистка и экспорт заблокированы, пока среда не готова или источник не подключён. Кнопка остановки остаётся доступна во время захвата. Демо не требует ни Python, ни датчика.
5. **«Остановить»** завершает захват, освобождает дескриптор и запускает извлечение сетки и цвета в фоне. Экспорт включится после обработки и подтверждённого повторного подключения источника. **«Отменить»** удаляет файлы нового незавершённого прохода; при отмене продолженного прохода ранее сохранённые кадры остаются как прерванный проход. **«Очистить»** очищает просмотр, но не удаляет сохранённые проходы.
6. В разделе **«Сохранённые проходы»** можно открыть или удалить готовый проход, продолжить прерванный тем же источником и выбрать не менее двух готовых проходов для объединения. Неудачно выровненные проходы исключаются из объединённого результата, их причины показываются в предупреждении.

Локальный API: `POST /api/devices/probe`, `/api/devices/connect`, `/api/devices/disconnect`; `GET /api/scan`, `/api/scan/passes`; `POST /api/scan/start`, `/api/scan/stop`, `/api/scan/cancel`, `/api/scan/clear`, `/api/scan/passes/select`, `/api/scan/passes/delete`, `/api/scan/merge`; `GET /api/export?format=ply|obj|glb` (необязательный `target` — идентификатор завершённого прохода). Кадры Kinect SDK 1.8 копируются через `CopyPixelDataTo` до освобождения .NET-кадра.

## Диагностика

### Ошибка установки pip (`pip_install_failed`) и другие сбои подготовки среды

Баннер настройки больше не ограничивается одной строкой: под сообщением есть

- **раскрываемые «Технические подробности»** — хвост вывода pip и код причины;
- **«Что проверить»** — подсказки под типовые причины: антивирус, свободное место, права на каталог, сеть/прокси/профиль сети. Вероятная причина помечена как «вероятная причина»;
- **«Скопировать журнал»** — копирует в буфер обмена код ошибки, причину, сообщение и хвосты `setup.log`, `pip-bootstrap.log` и `bridge.log`. Ничего никуда не отправляется автоматически: текст попадает только в буфер обмена на вашей машине.

Где искать точную причину:

| Файл | Что содержит |
|---|---|
| `%LOCALAPPDATA%\DepthStudio\logs\setup.log` | строки `INFO/WARN/ERROR` по этапам установки, включая вывод pip |
| `%LOCALAPPDATA%\DepthStudio\logs\pip-bootstrap.log` | только установка pip: попытки распаковки колеса, их вывод и ошибки |
| `%LOCALAPPDATA%\DepthStudio\logs\pip-install.log` | полный вывод `pip install` для NumPy/Open3D |
| `%LOCALAPPDATA%\DepthStudio\logs\selftest-report.json` | отчёт самопроверки (см. команду ниже) |

Самопроверка без графического интерфейса:

```powershell
& "$env:LOCALAPPDATA\Programs\Depth Studio\Depth Studio.exe" --depth-studio-selftest --report selftest-report.json
```

Файл отчёта по умолчанию — `%LOCALAPPDATA%\DepthStudio\logs\selftest-report.json`. Коды выхода: `0` — среда и мост готовы, `2` — настройка не удалась (деморежим остаётся доступным), `3` — непредвиденная ошибка.

Коды ошибок и что они означают:

| Код | Причина | Что делать |
|---|---|---|
| `pip_install_failed` | колесо pip не распаковалось или модуль `pip` не импортируется после распаковки | повторите; проверьте антивирус и `pip-bootstrap.log` |
| `pip_disk_full` | `ENOSPC`: на диске профиля закончилось место (нужно ≈ 600 МБ до установки пакетов) | освободите ≈ 1 ГБ; права администратора не нужны |
| `pip_access_denied` | `EACCES`/`EPERM`: нет прав записи в `site-packages` (права папки, Controlled folder access) | проверьте права на `%LOCALAPPDATA%\DepthStudio` и исключения антивируса |
| `pip_file_locked` | файлы среды удерживает другой процесс | закройте другие экземпляры Depth Studio |
| `packages_failed` | не установились NumPy/Open3D; причина уточняется в «Технических подробностях» | проверьте сеть/прокси, место, антивирус |
| `site_packages_not_writable` | проверка записи в `site-packages` не прошла до распаковки | права на каталог, антивирус |

Что делает установщик, чтобы сбой pip не был загадочным:

- **проверка записи до распаковки** — в `site-packages` создаётся и читается пробный файл, поэтому отказ доступа виден сразу, а не посреди установки;
- **проверка свободного места** — перед распаковкой pip и установкой пакетов; при нехватке места установка останавливается с понятным сообщением;
- **повтор распаковки** — частично распакованный pip (`pip/`, `pip-<версия>.dist-info`) удаляется и распаковывается ещё раз; нехватка места и отказ доступа повторно не пробуются (это не лечится повтором);
- **отдельный журнал** `pip-bootstrap.log` с перечнем попыток.

Остальные подсказки:

- **«Настройка среды не завершена — доступен деморежим»** — нажмите «Повторить», затем «Журнал установки». Деморежим работает всегда.
- **Загрузка Python не удалась** — проверьте интернет, прокси и антивирус; при повторной ошибке скачайте установщик заново (файл мог быть повреждён). Отключение проверки TLS не требуется и не поддерживается.
- **Open3D не импортируется** — чаще всего не хватает системного компонента Microsoft Visual C++ 2015–2022 Redistributable (x64). Установите его вручную с сайта Microsoft; Depth Studio не устанавливает системные компоненты автоматически. Деморежим, просмотр кадров и экспорт продолжат работать.
- **Мало свободного места** — среда занимает около 450 МиБ в профиле пользователя, само приложение ≈ 543 МБ, установщик ≈ 247 МБ.
- **Драйвер устройства Kinect не готов** — в правой панели блок «Драйвер устройства» показывает, чего не хватает: Kinect for Windows SDK 1.8 (вариант 1) или libusbK/WinUSB (вариант 2). Блок «Компоненты Python» относится к пакетам среды Depth Studio (`pythonnet`, `NumPy`, `freenect`).
- **Датчик не обнаружен** — проверьте блок питания, USB-подключение и не занято ли устройство другим приложением (Kinect открывается только одной программой).
- **Потеря трекинга / быстрое движение** — замедлите сенсор, верните в кадр уже просмотренную статичную поверхность и избегайте пустых однотонных стен.

## Как проверяется установщик

Workflow **Build Windows installer** содержит отдельную задачу `verify-installer`, которая:

1. скачивает готовый артефакт установщика и выполняет тихую установку (`/S`) в профиль пользователя — без прав администратора;
2. убирает Python из `PATH` и подставляет «ловушки» `python.bat` / `py.bat` / `python3.bat`, любой запуск которых вернёт ошибку, — так проверяется, что приложение не рассчитывает на системный Python;
3. запускает `Depth Studio.exe --depth-studio-selftest --report <файл>` и проверяет: код выхода, готовность среды, путь интерпретатора внутри `%LOCALAPPDATA%\DepthStudio`, Python 3.11.9, доступность NumPy/Open3D/**pythonnet**, изоляцию моста, версию, отданную `/api/health`;
4. повторяет самопроверку и убеждается, что среда переиспользуется (`cached = true`), то есть установка идемпотентна;
5. удаляет `site-packages\numpy` (оставляя `dist-info`) и убеждается, что следующий запуск восстанавливает среду, в том числе принудительной переустановкой пакетов;
6. запускает установленный Open3D-конвейер в отдельном процессе: сборку и экспорт меша, продолжение сохранённого прохода, аварийное завершение worker, синтетическую траекторию и бенчмарк; дополнительно проверяет CLR-массивы и `IntPtr`;
7. имитирует сбой установки пакетов (`DEPTH_STUDIO_ALLOW_TEST_HOOKS=1`) и проверяет код `packages_failed`, наличие журнала и доступность деморежима;
8. удаляет приложение и проверяет, что изолированная среда тоже удалена.

Отчёты и журналы складываются в артефакт **Depth-Studio-Clean-Install-Reports**.

Фактический результат последнего успешного прогона: первый запуск без Python — `Python 3.11.9`, `NumPy 1.26.4`, `Open3D 0.18.0`, среда 447,2 МиБ; повторный запуск — `cached = true` без переустановки; повреждённая среда восстановлена; смоделированный сбой дал код `packages_failed`, запись `ERROR` в журнале и доступный деморежим; удаление приложения очистило среду.

Важное ограничение: образ `windows-latest` от GitHub не является «чистой» Windows без Python — в нём Python предустановлен. Поэтому чистота среды обеспечивается:
- удалением всех каталогов Python из `PATH` для шагов, запускающих приложение;
- «ловушками» `python.bat` / `py.bat` / `python3.bat`, которые возвращают ошибку при любом обращении;
- проверкой, что отчёт самопроверки не видит ни одного каталога Python в `PATH` (`systemPathPython` пуст) и что `python.exe` находится внутри `%LOCALAPPDATA%\DepthStudio`.

Это воспроизводимая автоматическая проверка, но она **не заменяет** ручной прогон установщика на отдельной виртуальной машине без Python; такой прогон остаётся рекомендуемым шагом перед публикацией релиза.

```bash
npm run build          # рендерер
npm run dev            # интерфейс в браузере + прокси /api на 127.0.0.1:8765
npm run test:python    # тесты Python-моста и адаптеров датчиков
npm run test:desktop   # тесты среды первого запуска (повтор, восстановление, ошибки, pip)
npm run prepare:python # собрать встроенную среду Python для установщика
npm run check:python-bundle  # проверить контрольные суммы готовой встроенной среды
npm run check:python-lock    # проверить, что замок зависимостей полон для Windows
npm run resolve:python       # пересобрать Windows-замыкание зависимостей (нужен packaging)
```

Для тестов Python нужен NumPy: `python -m pip install packaging numpy` — тот же набор CI ставит перед `npm run test:python`. Тесты адаптера Kinect 360 используют поддельные `clr` и `Microsoft.Kinect`, поэтому железо и SDK для них не требуются; без NumPy они помечаются как пропущенные.

`start-windows.bat` — вспомогательный скрипт только для разработки интерфейса в браузере (деморежим, без установки). Он не настраивает датчик и не заменяет установленное приложение.

Версии Python-пакетов закреплены в двух файлах: `requirements-scan.txt` (прямые зависимости для чтения человеком) и `python-lock.json` + `requirements-scan.lock.txt` (полный набор с SHA-256, единственный источник истины для установки).

Важно: `pip download --platform win_amd64` выбирает правильные **колёса**, но маркеры окружения всё равно вычисляет на хосте сборки. Поэтому `colorama; sys_platform == "win32"` (нужен `ipython`) и подобные Windows-зависимости не попадают в замок, собранный на Linux. Для этого есть `scripts/resolve-windows-deps.py`: он обходит метаданные с маркерами Windows и добавляет недостающие пакеты, а `scripts/check-windows-lock.py` (запускается в CI) проверяет, что каждое Windows-требование закреплено и что SHA-256 колёс совпадает с PyPI.

После изменения зависимостей:

```bash
pip install packaging
npm run resolve:python              # Windows-замыкание: недостающие пакеты + колёса
python scripts/resolve-windows-deps.py --emit-lock  # перегенерировать замок без скачивания колёс
npm run lock:python                 # альтернатива: собрать замок из каталога колёс
npm run check:python-lock           # убедиться, что замок полон и хеши совпадают с PyPI
npm run prepare:python              # собрать встроенную среду для установщика
```

Прямые зависимости объявлены в двух местах: `ROOT_REQUIREMENTS` в `scripts/resolve-windows-deps.py` и `DIRECT_REQUIREMENTS` в `scripts/make-python-lock.mjs` (сейчас это `numpy`, `open3d`, `pythonnet`). `scripts/resolve-windows-deps.py` понимает сжатые наборы тегов колёс (`cp311.cp312…-none-any`), поэтому чистое колесо `pythonnet` попадает в замок наравне с колёсами `-cp311-win_amd64`.

Для диагностики без графического интерфейса:

```powershell
& ".\release\win-unpacked\Depth Studio.exe" --depth-studio-selftest --report selftest.json
```

Коды выхода: `0` — среда и мост готовы, `2` — настройка не удалась (деморежим остаётся доступным), `3` — непредвиденная ошибка.

Модульные проверки не заменяют аппаратные испытания: оба адаптера Kinect 360 по-прежнему требуют отдельной проверки на физическом датчике, а сценарий с `Microsoft.Kinect.dll` — ещё и на машине с установленным Kinect for Windows SDK 1.8.
